[前編](https://qiita.com/rex0220/items/43ceafa584690b4b0a5b) では、Claude Desktop のチャットで頼んで、見積書のデザインを作り込みました。後編では、同じアプリで見積書を新しく作り、**その見積書をもとに、注文書と請求書を「ベースに」「同じく」の一言で増やします**。

下は、同じレコードから出した見積書・注文書・請求書です。

![見積書・注文書・請求書.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/100572/73cdde93-ae6a-41cc-b832-205d46b68c3d.png)

この 3 つは、**5 つの作成・修正の依頼と、AI からの確認への回答だけ**で作りました。

| # | 頼んだこと | 結果 |
| :--- | :--- | :--- |
| 1 | `印刷屋で見積書の帳票を作りたい` → `3740` | AI が聞き返し、選択肢で答えて、型番付きの見積書ができた |
| 2 | （スクリーンショット）`社印が文字に重ならないように、中央に移動` | 社印の置き方を変えて直した |
| 3 | `見積書をベースに注文書を作成して` | 発注者の記入欄と押印欄のある注文書ができた |
| 4 | `同じく請求書を作成して` | 登録番号・振込先・お支払期限のある請求書ができた |
| 5 | `見積書・注文書・請求書を一つの設定ファイルにまとめて` | ボタンが 3 つ入った設定ファイルができた |

CSS や計算式は、今回も 1 行も書いていません。

アプリ番号を伝えてから、3 つをまとめた設定ファイルができるまで**約 12 分**でした（プレビューを見る・スクリーンショットを撮るといった人の作業を含む経過時間です）。注文書と請求書は、それぞれ頼んでから 2 分ほどでできています。

ただし、これは**ひな形ができるまで**の時間です。実際に運用するには、会社名・社印・登録番号・振込先といった仮の値の差し替え、取引条件（お支払期限など）や請求書の記載事項の確認、明細が多いときのページ分け、PDF での見た目の確認など、さらに細かな調整が要ります。調整もチャットで頼めますが、その時間はこの 12 分に含まれていません。

費用は、Claude の Max プランの定額の利用枠の中です。帳票ごとの追加料金はかかっていません。

> 拡張機能（印刷屋 設定オーサリング）の入れ方と、帳票を最初に作る手順は [最初の記事](https://qiita.com/rex0220/items/8cbebab5a5f8a9c21b1f) を見てください。本記事は、前編と同じ見積書アプリ（アプリ 3740）を使います。

# 1. 短く頼むと、AI が聞き返す

最初の記事では、アプリ番号・用紙・載せる項目・保存先まで書いて頼みました。今回は、ひとことだけです。

```
印刷屋で見積書の帳票を作りたい
```

AI はまず、拡張機能の準備ができているか（作業フォルダー、印刷屋の zip、kintone の接続）を確かめ、**アプリの番号を聞いてきました**。拡張機能の手順書が、名前でアプリを探したり似た名前から推測したりせず、番号を聞くよう AI に指示しています。`3740` と答えると、AI は次のことを自分で進めました。

| AI がしたこと | わかったこと |
| :--- | :--- |
| アプリの名前と項目定義を取る | 「見積書(印刷屋)」、項目 19。明細のテーブルに 単価・数量・型番・商品名・金額 |
| 今の印刷屋の設定を取り込む | ボタンが 13 ある（前編で作った 3 つを含む） |
| レコードを数件、**形だけ**見る | 明細が 5 行あるレコード 3 を、試し出力に使うことにした |

このレコードの確認で AI に返されたのは、実際の値ではなく、「明細 5 行」「商品名は最大 27 文字」のような行数や文字数などの情報です。ただし、後で貼るスクリーンショットのように、画像を貼ればそこに写る値は AI に渡ります。

そのうえで AI は、今回決める必要のあることを **2 つ、選択肢で**聞いてきました。

AI が選択肢で聞いてきた画面（2 問。選択肢ごとに説明が付き、「その他」に自由に書くこともできる）

![2026-10-11_13h20_08.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/100572/4b865687-b9dc-4b74-a488-30a10f5ab92c.png)

![2026-10-11_13h20_26.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/100572/dc88dd82-2d32-439b-90ad-8c27cdfff492.png)

| 聞かれたこと | 選択肢 | 選んだもの |
| :--- | :--- | :--- |
| 今回の見積書は、既存のボタンとどういう関係にしますか？ | 新しいデザインで別ファイル / 既存の 1 つを土台に改良 / 既存の設定にボタン追加 | 新しいデザインで別ファイル |
| PDF の保存先と、デザインの方向は？ | ダウンロード・型番列あり / 見積ファイルに保存 / ダウンロード・雛形どおり | ダウンロード・型番列あり |

2 問目の選択肢の説明には「既存は商品名/数量/単価/金額のみが多い」とあり、AI が今のボタンの明細の列まで見て選択肢を作ったことがわかります。答えるのはクリック 2 回です。要件を最初から全部書かなくても、今回は **AI がアプリを調べたうえで、必要な選択だけを聞いてきた**ので、短い頼み方で始められました。

できた見積書（ボタン名「見積書（型番付き）」）は、検査を通り、レコード 3 での試し出力は 1 ページ、式のエラーは 0 でした。返答には、次のような**確かめてほしい点**も書かれていました。

- 会社名「株式会社サンプル」と社印は、雛形のままの仮の値
- 明細はページを分けていないので、15〜18 行を超えると下が切れる（AI が示した目安で、商品名の折り返しなどで変わる）

# 2. 一言で直す — 社印が文字に重なる

会話の中のプレビューを見ると、社印が担当者の名前に重なっていました。前編と同じく、スクリーンショットを貼って頼みます。

```
社印が文字に重ならないように、中央に移動
```

貼ったスクリーンショット（社印が「担当: 営業太郎A」に重なっている）

![2026-10-11_13h22_35.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/100572/8a491f1a-4ff0-473a-8a36-9b4bb1825fea.png)

AI は原因を、**社印を文字の上に重ねる置き方**（`position: absolute` で右上から位置を決めていた）にあると見て、普通の並び方に変えました。社印は担当者の行の下、右の欄の中央に置かれ、名前と重なりにくい作りになりました。

直した後の見積書（社印が担当者の行の下に移った）

![2026-10-11_13h25_21.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/100572/41ecbf18-449f-4a8f-84fd-577cebb8bf94.png)

「中央」は、右の欄の中央とも、ページの中央とも読めます。AI は右の欄の中央と解釈し、返答にこう書いていました（要約です）。

> 「中央」がページ全体の中央（宛名欄と会社欄のあいだ）の意味だったら、そちらに寄せ直します。

今回は、**あいまいな言葉を AI がどう解釈したかも、返答に書かれていました**。違っていれば、もう一度頼むだけです。

# 3. 「ベースに」で派生させる — 注文書

見積書ができたので、同じ会話の続きでこう頼みました。

```
見積書をベースに注文書を作成して
```

できた注文書（会話の中のプレビュー）

![2026-10-11_13h27_09.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/100572/ce04376e-38b7-406a-b0d9-5c64fcd89653.png)

注文書は、誰が誰に出すかで中身が変わります。AI は**前提を 1 つ置いて**作り、返答の最初にそれを書いていました（要約です）。

> 見積先（宛名）が、株式会社サンプル宛てに出す注文書を、見積書と一緒に渡す形にします。発注者の欄は、会社名を宛名から入れ、住所・担当者・電話と押印欄を記入用にします。

見積書から変えたところです。

| 部分 | 見積書 | 注文書 |
| :--- | :--- | :--- |
| 題 | 御見積書 / QUOTATION | 注文書 / PURCHASE ORDER |
| 宛先 | 宛名 御中 | 株式会社サンプル 御中（向きが逆になる） |
| 本文 | 下記のとおりお見積り申し上げます。 | 貴社見積書に基づき、下記のとおり注文いたします。 |
| 右上 | 見積番号・発行日・有効期限 | 注文日（記入用の空欄）・見積番号・見積日 |
| 右の欄 | 会社名・担当者・社印 | 発注者の欄。会社名だけ宛名から入れ、住所・ご担当者・電話は記入用の線。押印の「印」の枠 |
| 下部 | 備考、小計・消費税・合計 | 希望納期・納入場所・お支払条件の記入欄を足し、その下に備考 |
| 末尾 | なし | 「ご記入・ご捺印のうえ、株式会社サンプル 担当（担当者）までご返送ください。」 |

明細の表、配色、ページ番号は見積書のままです。見積番号と見積日を入れたので、どの見積もりに基づく注文かがわかります。

CSS のクラス名は、見積書が `pcraft-q-` で始まるのに対し、注文書は `pcraft-po-` で始まります。前編の 3 パターンと同じく、帳票ごとにクラス名の頭を分け、後で 1 つの設定ファイルにまとめたときの CSS の干渉を避けやすくしています。

前提が違うときは、そう頼み直します。

```
自社が仕入先に出す注文書にして
```

```
対になる注文請書も作って
```

# 4. 「同じく」で通じる — 請求書

続けて、こう頼みました。

```
同じく請求書を作成して
```

できた請求書（会話の中のプレビュー）

![2026-10-11_13h28_37.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/100572/3d44d096-bc46-4044-8e14-c6352afbf712.png)

「同じく」だけで、**見積書をもとに、注文書と同じ作り方で**、という意味が通じています。同じ会話の中なので、AI は前の 2 つの設定を覚えています。

AI は書く前に、拡張機能の資料で日付の関数（今日の日付、月末）を調べ、次のように作りました。

| 部分 | 請求書 |
| :--- | :--- |
| 題 | 請求書 / INVOICE |
| 右上 | 請求日（PDF を出した日）、お支払期限（出した日の翌月末。強調）、見積番号 |
| 本文・金額 | 下記のとおりご請求申し上げます。ご請求金額（税込） |
| 右の欄 | 会社名の下に「登録番号 T0000000000000」、担当者、社印 |
| 下部 | お振込先（銀行・口座名義・振込手数料の注記）の欄と、その下に備考 |
| 合計 | 「10%対象 小計」「消費税（10%）」「合計」 |

今回は、明細がすべて 10% 対象の例です。お支払期限の「翌月末」は、AI が置いた仮の条件です。注文書の「誰が誰に出すか」と同じく、自社の取引条件に合わせて頼み直します。

請求日とお支払期限は、計算式で今日の日付から作っています。

```
${DATE_FORMAT("TODAY", "YYYY年M月D日")}
${DATE_ENDOF(DATE_ADD("TODAY", 1, "month"), "month", "YYYY年M月D日")}
```

## 検査の警告を、AI がどう扱ったか

請求書では、検査が警告を 1 つ足しました。`${…}` が文字列をエスケープせずに差し込んでいる、という警告（`html.rawExpression`）です。

AI はこの警告を消さずに伝え、残した理由をこう書いていました（要約です）。

> 中身は今日の日付から作る、決まった書式の日付で、レコードの値は入らないので、そのままにしています。警告を消したい場合は `ESC_HTML` で包みます。

この拡張機能は、検査の結果（警告を含む）を**省略せず、利用者に伝える**よう AI に指示しています。残すか直すかは、理由を読んで人が決めます。

## 仮の値と、運用の注意

返答の最後には、差し替えが要るところと、運用の注意がまとめてありました。

- 登録番号と振込先（○○銀行 ○○支店 …）は仮の値
- 請求日は PDF を出した日なので、出し直すと日付が変わる。固定したいなら、アプリに「請求日」の日付項目を足して、それを使うように頼む
- 取引年月日（納品日など）は今は載っていない。項目があれば足せる

# 5. 1 つの設定ファイルにまとめる

最後に、3 つを 1 つのファイルにしてもらいました。

```
見積書・注文書・請求書を一つの設定ファイルにまとめて
```

できたのは、ボタンが 3 つ入った `見積書・注文書・請求書.json` です。個別に作った 3 つのファイルも残っています。

- 検査の結果: 警告 4 件（3 つのボタンの `TABLE_HTML` と、請求書の日付の式）、保存値 6,561 bytes（上限の 3%）
- 試し出力: 3 つとも 1 ページ、式のエラー 0。会話の中にプレビューが 3 つ並ぶ

取り込みは、印刷屋の設定画面の **設定をアップロード** です。

設定のアップロードの画面（「追加」を選んだところ。3 つのボタンが、同じ名前のまま末尾に足される）

![2026-10-11_13h51_10.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/100572/a4604f5e-ced7-45c5-8101-cb83cb1f3f99.png)

- まだ個別のファイルを取り込んでいなければ **追加**。今のボタンの後ろに 3 つ並ぶ
- 個別のファイルを取り込み済みなら **一部置換** で、同じ名前のボタンを置き換え先にする。「追加」だと「見積書（型番付き） (2)」のように同じボタンが重なる

画面の「メモ」には、AI が設定ファイルに書いた説明（3 つのボタンと、それぞれのクラス名の頭）が出ます。「外部参照・Web フォント・メニュー…は今の設定のままです」とあるとおり、「追加」ではアプリの共通の設定は変わりません。

保存して運用環境に反映すると、詳細画面に「見積書（型番付き）」「注文書」「請求書」のボタンが並び、同じレコードから 3 つの PDF を出せます。

# 帳票を増やすときのコツ

## 同じ会話の続きで頼む

「ベースに」「同じく」が通じるのは、AI が同じ会話の中で作った設定を覚えているからです。新しい会話で頼むときは、もとにする設定のファイル名を伝えます。

```
作業フォルダーの「見積書（型番付き）.json」をもとに、納品書を作って
```

## AI が置いた前提を読む

注文書の「誰が誰に出すか」のように、帳票は前提で中身が変わります。返答に書かれた前提を確認し、違っていればその場で言い直します。

## 日付の意味は帳票ごとに違う

同じ「日付」でも、見積書は見積日（項目）、注文書は記入用の空欄、請求書は PDF を出した日（今日）と、意味が違います。決まった日付を載せたいなら、アプリに項目を足して、それを使うように頼みます。

## クラス名の頭を分ける

帳票ごとにクラス名の頭（`pcraft-q-` / `pcraft-po-` / `pcraft-bill-`）を分けておくと、1 つの設定ファイルにまとめても CSS の干渉を避けやすくなります。AI は頼まなくても分けて書きましたが、気になるなら「クラス名の頭を帳票ごとに分けて」と頼めます。

# 気を付ける点

- **請求書の記載事項は、自社で確かめる**: 今回の請求書には登録番号の欄と、10%対象の小計・消費税額が入りましたが、登録番号は仮の値で、取引年月日は載っていません。適格請求書として使う場合は、必要な記載事項（[国税庁の説明](https://www.nta.go.jp/taxes/shiraberu/taxanswer/shohi/6625.htm)）と自社の取引の内容に合っているかを、経理や税理士に確かめてください
- **仮の値を残さない**: 会社名・社印・登録番号・振込先は仮の値で入ります。取り込む前に差し替えてもらいます
- **1 ページに収まる行数**: 3 つともページを分けていません。明細が多い見積もりがあるなら、「明細を複数ページに分けて」と頼みます
- **プレビューは近似**: 書体や細部は、印刷屋の PDF で確かめます（[前編](https://qiita.com/rex0220/items/43ceafa584690b4b0a5b) の「気を付ける点」も見てください）
